# ADR-0006: Authentication — email + password, cookie sessions; OAuth — post-MVP

**Status:** accepted
**Date:** 2026-10-22

## Context
The requirements do not describe sign-in (digest §4, question 1) but need identity: the project owner (US-05 403), "my applications" (US-13), one application per role (US-12 sc.3), contact disclosure (US-14). We need the cheapest way to close the gap without external services.

## Options
### A. Email + password, server-side sessions in a cookie (httpOnly)
+ zero external dependencies and keys; works offline at the demo
+ sessions in a cookie — the browser sends them itself; the CSRF risk is minimized with SameSite=Lax (SPA and API on one origin, ADR-0008)
− password storage (bcrypt) is the team's responsibility; password recovery is out of the MVP

### B. GitHub OAuth
+ students have GitHub; the profile immediately contains a GitHub link for US-12
− OAuth App + secrets for every developer; callback URL for local/prod; dependency on an external service during the demo

### C. Telegram Login Widget
+ Telegram username (US-01) — out of the box
− requires a bot and a public domain even for development; the least material

### D. No authentication, identity = Telegram username from the form
+ zero code
− anyone can impersonate anyone, look at others' applications, "approve" someone else's candidate. Violates US-05 sc.3, US-14 sc.2.

## Decision
**A.** The minimum: registration (email, password, display name), sign-in, sign-out, `GET /me`. The Telegram username is set in onboarding (US-01) and pre-filled in the application form (US-12) — both stories are satisfied without contradiction.

## Consequences
+ one `requireAuth` middleware, one Session table (or a signed cookie)
− no password recovery and no email verification — accepted for the MVP
Revisit: after the MVP, add GitHub OAuth as a *second* sign-in method (the User model does not change: a `githubId` is added).
